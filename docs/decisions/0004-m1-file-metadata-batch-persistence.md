# ADR 0004：M1.2 文件元数据批量持久化

- 状态：已接受
- 日期：2026-09-01
- 范围：`crates/nexus-db`

## 背景

M1.1 已经能够以 `Iterator` 逐项遍历目录，并把文件、跳过和单项失败结果流式交给上层。下一步需要把成功读取的文件元数据写入 SQLite，同时保留单个文件在扫描期间被删除、修改或无法读取时的失败统计。

如果先把所有记录收集到内存，再一次性写入，无法满足长期的大目录规模，也会把单个记录问题和整个数据库事务混在一起。因此需要一个位于数据库边界内、内存有界的批量写入入口。

## 决策

### 1. 批量写入属于数据库层

`nexus-db` 提供 `upsert_file_metadata_batch`，调用方传入可消费的结果迭代器和正整数批次大小。数据库层只处理 `FileMetadata` 及其持久化错误，不依赖扫描器、Tauri 或 UI。

### 2. 每个批次使用独立事务

一个批次先收集不超过配置上限的有效记录，再在一个 SQLite 事务中执行现有的 upsert 语句。事务提交成功后才增加已写入和批次数；批次之间互不回滚。

批次大小为零会在消费输入前返回明确错误。批次缓存复用容量，不要求把整个扫描结果载入内存。

### 3. 单条错误可统计，数据库错误仍需返回

输入的 `Err(FileMetadataError)` 和元数据校验错误计入 `FileMetadataBatchSummary.failed`，随后继续消费剩余输入。`received` 统计所有输入项，`written` 统计成功提交的 upsert，`batches` 统计成功提交的事务。

SQLite 连接、事务开启、SQL 执行或事务提交失败不被伪装成单条记录失败，而是直接返回带安全分类的数据库错误。这些错误说明持久化边界本身不可用，应由上层决定如何结束当前任务。

### 4. 暂不在此单元做重扫一致性

M1.2 只提供可靠的批量写入能力，不根据一次扫描结果删除旧记录，也不负责目录选择、取消、后台任务或 UI 进度。新增、更新、移除的重扫语义和完整统计留给 M1.3。

## 结果与取舍

- 事务批次降低了逐条提交的开销，同时把缓存内存限制在批次范围内。
- 单条扫描失败不会阻止其他成功元数据提交，调用方可以得到确定性失败数量。
- 数据库级失败仍可能在已提交若干批次后停止任务；这是避免静默丢失或伪造成功状态的有意选择。
- 没有新增第三方依赖，继续使用现有的 `rusqlite + bundled`。

## 验证

- 批次大小为零时不会消费输入。
- 五条记录按两条一批提交，得到三个成功事务。
- 输入错误和无效文件大小被计数，其他有效记录继续写入。
- 100,000 条合成文件元数据按 1,024 条一批写入并验证最终行数。
