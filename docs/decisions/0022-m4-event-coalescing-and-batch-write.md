# ADR 0022：M4.2 事件归并与批量写入

## 状态

已接受（2026-09-01）

## 背景

M4.1 已经能够把操作系统通知转换为统一的文件事件，但同一个保存动作可能产生多次
创建、修改或重命名通知。若每个通知都立即解析和写入，容易重复工作，也可能在文件
仍处于写入过程中时保存不完整正文。

## 决策

在 `nexus-core` 增加事件归并和增量处理边界：

- `EventBatcher` 以 250ms 安静窗口合并短时间内重复事件；一个批次最多保留 128 个不同路径。
- 同一路径只保留最终操作，创建/修改归并为更新，删除归并为移除；重命名拆成旧路径移除
  和新路径更新，完整重扫信号覆盖尚未提交的局部事件。
- 批次中的路径按稳定顺序输出，便于测试和诊断。
- 更新文件时先读取元数据、解析正文，再次读取元数据；状态变化时短暂等待并重新确认。
- 单文件解析失败不覆盖已有 canonical 正文；数据库事务失败则整个批次回滚并最多重试两次。
- `nexus-db::apply_file_mutations` 在一个 SQLite 事务中同时维护 `file_metadata`、
  `documents` 和 FTS trigger 产生的索引状态。

## 取舍

### 以最终路径操作为准

事件顺序不可靠时，归并器不把通知列表当作事实，而是让增量处理重新读取当前文件状态。
这样删除后又创建的路径最终会重新更新；已经消失的更新事件最终会转为移除。

### 解析失败保留旧正文

编辑器保存期间或文件损坏时，旧正文仍然比半截新正文更可靠。后续事件、手动重扫或
重启恢复可以再次尝试；本次失败只计入批次统计，不让单文件阻断其他路径。

### 事务失败按批次重试

批次内所有元数据、正文和 FTS 变化一起提交，避免只更新一部分。重试次数有限，避免
数据库持续不可用时后台任务无限阻塞；M4.3 负责把最终失败报告给桌面任务并继续监听。

## 后续影响

- M4.3 可以在后台线程中持续消费 `FileWatcher`，在安静窗口或路径上限达到后调用当前
  增量处理入口。
- 当前单元还不负责 watcher 的线程生命周期、应用关闭和重启恢复。
- 当前默认使用现有解析资源上限，不引入新的解析格式或网络行为。
