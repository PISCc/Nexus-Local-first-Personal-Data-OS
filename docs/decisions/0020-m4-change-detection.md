# ADR 0020：M4.0 文件变化判定

## 状态

已接受（2026-09-01）

## 背景

M3.6 已经能够对用户指定目录建立初始正文索引，但每次后续处理仍需要把目录中的文件重新交给完整索引流程。M4 的第一步需要先回答一个更基础的问题：两次看到的文件状态之间，哪些文件真的需要重新处理。

当前数据库中的文件元数据已经包含路径、大小和修改时间；扫描器也会逐条产生同样的文件元数据。这个能力可以先独立于监听器和桌面任务验证。

## 决策

在 `nexus-core` 增加独立的变化判定模块：

- 用路径作为文件身份。
- 用大小和修改时间作为当前阶段的廉价状态信号。
- 输出新增、修改、未变化和已消失四类结果。
- 结果按路径排序，便于后续批处理、测试和诊断保持稳定顺序。
- 修改时间缺失时采取保守策略：即使大小相同，也判定为需要重新处理。
- 同一输入侧出现空路径或重复路径时返回明确错误，不静默覆盖输入。

变化判定只比较调用方提供的快照，不读取正文、不计算 hash、不写数据库，也不监听文件系统。未来的文件事件、去重、防抖和增量持久化都应复用该结果，但不由本单元提前决定。

## 取舍

### 不在本单元引入文件监听依赖

M4.0 的目标是验证变化分类本身。提前绑定操作系统 watcher 会同时引入事件语义、关闭顺序、重复事件和平台差异，扩大本单元的验证面。M4.1 再根据实际桌面需求选择事件来源，并保持其与扫描/判定逻辑解耦。

### 暂不使用 hash

大小和修改时间足以覆盖常见的新增、编辑和删除场景，且不需要读取用户正文。若后续真实文件系统存在时间精度不足或原子保存竞态，再在明确的重检路径中评估 hash，而不是让每次索引默认读取全部内容。

### 将“无法确认稳定”视为修改

若修改时间缺失，系统无法证明同大小文件没有变化。保守地重新处理可能增加少量工作，但不会把旧正文错误地当作最新正文，符合可靠性优先原则。

## 后续影响

- M4.1 可以把 CREATE、UPDATE、DELETE、MOVE/rename 事件转换为快照或重检请求。
- M4.2 可以在批处理前合并同一路径事件，并使用 `files_needing_processing` 作为候选数量。
- 当前仍不能自动感知文件变化；桌面界面仍使用 M3.6 的手动初始索引入口。
- 移动文件在本单元仍表现为旧路径消失加新路径新增；移动身份识别留给后续单元。
