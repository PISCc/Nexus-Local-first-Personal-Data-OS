# ADR 0021：M4.1 文件事件来源

## 状态

已接受（2026-09-01）

## 背景

M4.0 已经能够比较两次文件状态，但系统还没有接收文件系统实时变化的入口。M4.1 需要把不同平台的创建、修改、删除和重命名通知转换成 Nexus 可以理解的统一事件，同时保持监听器与扫描、解析和数据库逻辑分离。

架构文档早期已经把 Rust `notify` 列为文件监听方案。本单元只实现事件来源适配，不提前实现事件去重、防抖或增量写入。

## 决策

在 `nexus-core` 使用稳定版 `notify 8.2.0`，增加 `watch_directory` 和 `FileWatcher`：

- 递归监听调用方指定的根目录；
- 将底层事件转换成 `FileEvent::Created`、`Modified`、`Removed` 和 `Renamed`；
- 只输出监听根目录及其子路径，范围外事件被忽略；
- 支持底层一次提供两端路径的重命名，也支持连续的 From/To 重命名通知配对；
- 底层报告事件可能丢失时输出 `RescanRequired`，要求后续流程进行完整重扫；
- `FileWatcher` 的生命周期决定监听生命周期，丢弃 watcher 即停止监听；
- 底层错误转换为不包含路径、文件名或原始错误文本的安全错误分类。

事件只携带路径，不在监听回调中读取正文、读取元数据或写入数据库。后续消费者自行决定何时重新扫描路径并交给 M4.0 变化判定。当前只对相邻的 From/To 通知进行配对；更复杂的事件合并、去重和防抖留给 M4.2。

## 取舍

### 使用 `notify` 而不是自建平台 API

`notify` 已经封装 Windows、Linux 和 macOS 的底层差异，符合仓库既定技术栈，也避免在核心层维护平台相关代码。依赖固定到稳定版 `8.2.0`，不采用预发布版。

### 监听器只产出事件，不直接触发索引

监听回调可能在文件仍处于写入过程时触发。若回调直接读取正文或写数据库，会把监听线程、文件稳定性和持久化一致性绑在一起。先输出统一事件，后续由批处理层等待、重检和决定处理顺序。

### 对事件丢失采取完整重扫

底层通知队列溢出或系统重建监视状态时，局部事件列表不再可靠。输出 `RescanRequired` 比继续假设局部状态完整更安全；M4.2/M4.3 再决定如何调度这次重扫。

## 后续影响

- M4.2 可以把同一路径的连续事件合并，避免重复解析。
- M4.3 可以在后台任务中持有并关闭 `FileWatcher`，并把取消与应用关闭接入任务生命周期。
- 当前事件来源已可测试，但尚未自动更新 `file_metadata`、`documents` 或 FTS。
- 移出监听范围的重命名表现为 `Removed`，移入监听范围的重命名表现为 `Created`；跨范围身份识别留给后续数据层。
