# ADR 0012：M2.3c PDF 解析边界

- 状态：已接受
- 日期：2026-09-01
- 范围：`crates/nexus-core`

## 背景

M2.3a 和 M2.3b 已分别建立 HTML、DOCX 到统一文本 `Document` 的单文件解析边界。
M2.3c 需要处理本地 PDF，同时面对二进制 PDF 结构、压缩流、字体编码、页序和损坏输入。
当前目标仍是可靠的本地文本基础，不提前建立正文数据库、批量调度或页码位置模型。

## 决策

### 1. 使用 `lopdf 0.44.0` 的有界文本提取能力

`nexus-core` 增加：

- `lopdf = { version = "0.44.0", default-features = false }`；关闭默认的日期、并行和
  时间特性，保留 PDF 读取、解压、字体编码和文本提取所需能力。
- `LoadOptions::with_max_decompressed_size` 限制加载阶段单个解压流。
- `Document::extract_text_with_limit` 限制页面文本提取阶段单个页面内容和字体映射流的
  解压大小。

选择 `lopdf` 而不是 `pdf-extract` 的原因是本单元需要把解压资源边界作为公开解析合同的
一部分；`lopdf` 直接提供与这些边界对应的加载和页面提取 API。依赖版本、许可证和 API
以 [lopdf 0.44.0 官方文档](https://docs.rs/lopdf/0.44.0/lopdf/) 为准。

### 2. 保持单文件显式 API

公开入口为：

```text
parse_pdf_file(document_id, path, max_input_bytes, max_decompressed_bytes, max_output_bytes)
    -> Result<Document, ParseError>
```

调用方提供原始 PDF 文件上限、单个解压流上限和提取后正文上限。解析器只处理一个扩展名
大小写不敏感的 `.pdf` 普通文件；正文在内存中处理，不把 PDF 内容写入临时文件。

### 3. 按逻辑页序生成统一正文

解析器从 `get_pages()` 得到 PDF 的逻辑页码，逐页调用有界文本提取，按页码顺序处理。
每页文本裁剪两端空白；空页不产生正文；非空页面之间使用两个换行连接。这样页面边界
对后续词法搜索可见，但不把页面专属结构写入 `Document` 正文或新增字段。

标题使用完整文件名，来源使用规范化后的本地路径，位置使用
`DocumentLocation::whole_document()`。本单元不增加页码、字符偏移或渲染坐标字段。

### 4. 明确错误和资源行为

三个大小上限必须大于零。原始 PDF 超限沿用 `parse_file_too_large`；解压流超限返回
`parse_pdf_content_too_large`；提取正文超限沿用 `parse_output_too_large`。损坏或不支持的
PDF 返回 `parse_pdf_invalid`，第三方解析器 panic 在边界内转换为
`parse_pdf_parser_failed`。错误展示不包含路径、文件名、PDF 正文、对象内容或底层错误
字符串；底层 `lopdf` 错误只通过进程内 `Error::source` 保留诊断信息。

解析器不渲染页面、不执行 OCR、不处理密码、不读取附件、嵌入媒体或外部链接，不访问
网络，不写 SQLite，不发送 UI 事件。扫描到一个失败 PDF 后，调用方仍可处理后续文件。

## 备选方案

- `pdf-extract`：提供较高层的按页文本接口和更专门的字体/编码依赖，但当前版本的公开
  内存提取入口没有把解压上限直接暴露给调用方；在本单元的安全边界要求下，暂不采用。
- 直接使用 `lopdf` 的无界 `extract_text`：实现更短，但会放弃对页面内容解压的明确保护，
  因此使用有界版本。
- 手写 PDF tokenizer 或只识别 `BT/Tj/ET`：会丢失字体编码、对象流、交叉引用和真实语料
  兼容性，维护风险高，因此不实现。
- 扩展 `DocumentLocation` 保存页码、字符偏移或坐标：当前搜索层还未消费这些字段，提前
  改变公共模型会增加迁移成本，因此保留 whole-document。

## 结果与取舍

- 新增 `lopdf 0.44.0` 是本单元的主要依赖变更；关闭默认 feature 可减少无关平台能力，
  但其 PDF 解析仍会带入解压、加密、字体编码和 Unicode 相关依赖。
- PDF 解析器需要在内存中保留受限的原始文件、PDF 对象结构和当前页面文本；输入、解压流
  和输出上限约束了当前可观测边界，但对象数量、跨对象引用复杂度和整体峰值内存仍需用
  真实语料持续测量。
- 文字型 PDF 可以进入统一正文；扫描件或只有图片的 PDF 不会因为本单元而获得 OCR 文本，
  复杂字体的文本映射也可能不完整。这些能力留给后续独立评估。
- 对轻微结构损坏的 PDF 沿用库的容错读取策略；无法恢复的输入返回错误，不允许 panic 穿透
  核心边界。第三方库错误内容不进入用户消息或默认日志。

## 验证

- 覆盖两页 PDF 的页序、标题、来源、whole-document 位置和空白页边界行为。
- 覆盖无效 PDF、安全错误展示、原始输入上限、解压流上限、提取输出上限、大小写扩展名
  和零限制。
- 使用隔离临时目录和库生成的最小 PDF fixture；不读取真实用户目录，不写临时解压文件，
  不访问网络，不写 SQLite。
