# ADR-0018：M3.5 搜索质量评估

- 状态：Accepted
- 日期：2026-09-01
- 范围：M3.5 搜索质量评估

## 背景

M3.1–M3.3 已经固定了 SQLite FTS5、`unicode61 remove_diacritics 1`、受限查询语法、
标题优先的 BM25 权重和有限 snippet，但这些选择还没有经过可重复的质量测量。M3.5
需要回答两个问题：当前 lexical ranking 是否比 M3.2 的稳定文档 ID 顺序更能把相关结果
放在前面，以及当前小规模索引的查询和存储成本是多少。

## 决策

### 1. 使用仅测试可见的离线评估 harness

新增 `crates/nexus-db/tests/search_quality.rs`，直接调用已有的
`nexus_db::search_documents`。harness 不新增生产 API、不写用户数据库、不读取真实用户
文件，也不引入新依赖；固定语料通过 `DocumentRecord` 写入临时 SQLite 数据库。

### 2. 固定小型代表性语料和人工相关性标注

语料包含 10 条代表本地项目计划、会议记录、备份、隐私、数据库、搜索研究和代码索引的
英文文档；查询集包含 9 个关键词/短语查询，每个查询有明确的相关文档 ID 集合。使用
合成但贴近实际工作的内容，避免把个人数据带入仓库。当前 tokenizer 对中文分词的能力
仍单独记录为风险，不在本单元用不稳定的中文匹配结果伪造结论。

### 3. 同时测量质量、延迟和索引占用

- 质量使用每个查询的 Recall@3，并汇总为 macro Recall@3；同时记录 Top-1 命中数。
- 每个查询执行 15 次，记录中位延迟和 p95 延迟；延迟只作为观测值，不设置易受机器
  波动影响的硬阈值。
- 记录 SQLite 文件总字节数，以及 FTS5 `documents_fts_data` segment block 的字节数。
  前者包含 canonical 文档和 FTS，后者是当前 schema 下的 FTS segment 存储代理值。

### 4. 用 M3.2 的排序作为可解释基线

对每个查询先取同一候选集合，再按 `document_id COLLATE BINARY ASC` 重排，作为 M3.2
无 ranking 时的基线。当前 FTS5 BM25 结果与该基线并列打印；测试要求当前 Recall@3
不得低于基线。该基线用于比较排序修改的影响，不等同于人工标注的绝对质量上限。

## 未采用的方案

- **读取真实用户文件或搜索历史**：违反本地优先和隐私边界，且无法提交可复现的测试。
- **引入 benchmark/统计依赖**：当前样本量小，标准库的 `Instant`、排序和百分位计算已足够。
- **把延迟写成固定通过阈值**：不同机器、文件系统和 Debug/Release 模式会造成无意义的
  波动；先记录数据，后续再决定是否需要正式性能门槛。
- **在本单元调整 tokenizer、权重或引入语义 reranker**：评估应先观察现状，避免把测量
  和算法变更混在一起。

## 风险和后续影响

- 10 条英文语料和 9 个查询只能发现明显的排序回归，不能代表中文、PDF、DOCX 或大规模
  个人资料的真实召回质量。
- FTS segment 字节数不是操作系统文件分配量，也不包含所有 shadow table 和 SQLite 页面
  开销；报告同时保留 SQLite 文件总大小以避免误读。
- 后续若使用真实脱敏语料或扩大查询集，应保留查询标注版本，并在后续验收中重新记录。
