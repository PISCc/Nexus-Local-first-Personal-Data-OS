# ADR 0009：M2.2 JSON 解析边界

- 状态：已接受
- 日期：2026-09-01
- 范围：`crates/nexus-core`

## 背景

M2.1 已经建立了单文件 UTF-8 文本解析和统一 `Document` 输出。M2.2 需要为
JSON 增加合法性和资源边界，同时保持解析器不依赖 UI、不写入数据库，也不提前
进入批量调度或全文搜索。

## 决策

### 1. 使用现有生态中的 serde_json 作为直接依赖

`nexus-core` 增加锁定版本的直接依赖 `serde_json = "1.0.151"`，使用成熟的
JSON 语法实现，不手写 JSON 解析器，也不使用正则表达式猜测合法性。

### 2. 保持单文件显式 API

公开入口为：

```text
parse_json_file(document_id, path, max_bytes, max_depth)
    -> Result<Document, ParseError>
```

文档 ID、文件路径、正文大小上限和嵌套深度上限均由调用方提供。解析器只读取
一个 `.json` 文件，扩展名大小写不敏感；来源、标题和 whole-document 位置沿用
M2.0/M2.1 的 `Document` 规则。

### 3. 保留原始 JSON 文本

文件正文必须是合法 UTF-8；只移除开头的 UTF-8 BOM，保留 JSON 的空白、换行、
缩进、字段顺序和其他原始文本。解析器不格式化、排序字段或生成规范化 JSON，
避免在进入后续存储和搜索层之前丢失用户文件的可追溯文本形态。

### 4. 明确大小和嵌套深度边界

`max_bytes` 必须大于零。解析器先检查普通文件元数据，再执行有界读取，并检查
读取期间文件是否增长超过上限。JSON 解析成功后计算容器嵌套深度：根标量为 0，
根对象或数组为 1，每进入一层对象或数组增加 1；实际深度大于 `max_depth` 时
返回错误。

### 5. 固定错误和副作用边界

新增 `ParseError::InvalidJson` 和 `ParseError::JsonTooDeep`，分别映射为
`parse_json_invalid` 和 `parse_json_depth_exceeded`。文件元数据、普通文件、打开、
读取、大小限制、UTF-8 和 `Document` 构造错误沿用 M2.1 分类。

`Display` 和用户消息不包含路径、文件名、正文或原始系统错误；底层 JSON 错误只
通过进程内错误链保留。解析失败不写数据库、不发送 UI 事件、不上传内容，也不会
阻止调用方继续处理后续文件。

## 备选方案

- 先把 JSON 反序列化后重新格式化：输出会丢失原始空白和字段顺序，不利于内容追溯，
  因此保留原文。
- 手写 JSON 解析器：会重复实现成熟库的语法和错误处理，增加正确性风险，因此使用
  `serde_json`。
- 不限制嵌套深度：极端结构会增加解析资源风险，因此由调用方明确提供上限。
- 提前抽象通用 Parser trait 或批量调度器：当前没有第二种格式或调度需求，留给后续
  单元，避免扩大公共边界。

## 结果与取舍

- M2.2 不改变 `Document` 数据模型，不修改 SQLite schema，不接入 Tauri、React 或
  M3 全文搜索。
- JSON 正文在去除 BOM 后保持原始文本；`serde_json::Value` 仅作为解析期间的临时
  校验结构，不作为新的持久化模型。
- `max_bytes` 限制原始文件大小；当前实现会在深度检查前构造临时 JSON 值，因此极深
  但仍未超过字节上限的输入仍可能消耗解析内存，这属于后续需要实测和优化的边界。

## 验证

- 覆盖合法 JSON、大小写扩展名、原始文本保留、根标量深度 0、超深 JSON、malformed
  JSON、无效 UTF-8、超限文件、目录和不支持扩展名。
- 使用隔离临时目录测试；不读取真实用户目录，不执行批量解析或网络操作。
