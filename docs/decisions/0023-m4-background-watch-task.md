# ADR 0023：M4.3 后台监听任务与关闭

## 状态

已接受（2026-09-02）

## 背景

M4.2 已经具备事件归并、文件稳定性确认和单批次事务写入能力，但这些能力仍需要一个
长期运行的生命周期边界。桌面界面不能承担持续等待文件事件的工作；应用关闭时也必须
停止接收新事件，并等待正在进行的处理安全退出。

## 决策

在 Tauri 桌面层增加一个轻量的 `WatchManager`：

- 每次只允许一个后台监听任务；任务在独立线程中持有 `FileWatcher` 和 `EventBatcher`，
  UI 命令只负责启动、查询和停止，不直接处理事件或数据库。
- 监听任务使用已有的 `RescanControl` 和独立关闭标记。取消或应用退出时先停止继续接收
  新事件，再等待后台线程结束；未提交的批次不会绕过核心层的数据库事务边界。
- 增量批次暂时无法提交时保留该批次并按有界间隔重试，同时继续保持可取消；成功后才向
  UI 发布统计，不把文件路径、正文或底层错误文本放入事件。
- 一次包含正文的初始索引成功后，将用户明确输入的目录保存到应用本地数据目录。下次
  启动时先对该目录进行一次完整本地索引，再重新开启监听，以覆盖应用关闭期间的文件变化。
- 监听启动失败、状态读取失败和目录配置读写失败只返回或记录固定安全分类；不上传任何
  文件、路径或搜索数据。

## 边界

本决策只覆盖桌面任务生命周期、取消、关闭和启动恢复。文件事件归一化由 M4.1 负责，
事件归并、稳定性确认和事务写入由 M4.2 负责；不新增解析格式、不改变搜索、不进入
语义检索或云端同步。

## 取舍

### 独立线程而非 UI 轮询

文件通知的等待和增量处理不占用界面线程，窗口仍可响应。线程数量保持为单个监听任务，
避免为了早期功能引入异步运行时或复杂任务调度器。

### 关闭时等待退出

关闭流程明确发出取消并等待线程结束，能够保证 watcher 被释放、未完成事务不会继续写入。
极慢的单文件解析仍可能让关闭等待一小段时间，但不会留下后台线程继续使用应用状态。

### 启动时完整恢复

恢复阶段重新扫描已保存目录，比猜测应用关闭期间遗漏了哪些事件更可靠。恢复使用已有
索引入口，不保存事件队列，也不要求网络或额外服务。

## 后续影响

- UI 增加监听状态和最近一次增量统计，但不展示敏感路径或正文。
- 本地数据目录多一个仅用于恢复监听根目录的小配置文件；原始文件和数据库位置策略不变。
- M4.4 继续验证真实文件移动、原子保存、重复事件及重新打开后的最终一致性。
