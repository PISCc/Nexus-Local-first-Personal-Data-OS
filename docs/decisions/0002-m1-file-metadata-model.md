# ADR-0002：M1.0 文件元数据模型

- 状态：已接受
- 日期：2026-08-31
- 范围：M1.0 文件元数据模型

## 背景

M1 需要把本地文件的最小信息保存到 SQLite，供后续递归扫描、手动重扫和增量索引使用。
本单元还没有扫描器、正文解析或全文搜索，因此不能提前引入通用文档模型、文件监听或
哈希计算。

## 决定

1. 在 schema 版本 2 中增加 `file_metadata` 表，不创建正文表或全文索引。
2. 文件记录保存路径、文件名、扩展名、大小、三个可选时间戳和可选的类型标签。
3. 时间戳统一保存为 Unix epoch 毫秒；平台无法提供的时间使用 `NULL`。
4. 路径先绝对化，但不执行 `canonicalize`，不解析符号链接，也不进行大小写折叠。
5. 数据库使用平台相关的路径原始表示作为 `path_key`，同时保存安全的 `path_display` 展示值。
   这样路径无法直接转换为 UTF-8 时也不会导致程序崩溃或丢失主键身份。
6. `file_type` 只接受调用方提供的可选标签；M1 不读取文件内容，也不进行 MIME 猜测。
7. 不默认计算哈希。只有后续需求或测量证明必要时，才单独评估哈希成本和存储方式。
8. `nexus-db` 提供模型、迁移、单条 upsert 和按路径读取入口；不新增 Rust crate，扫描流程留给后续单元。

## 取舍

- 使用 `path_key` 而不是只保存 UTF-8 路径，会增加一列展示值和平台编码代码，但可以避免
  非 UTF-8 路径碰撞，也不需要依赖第三方路径编码库。
- 不执行 `canonicalize` 意味着不同的等价路径表达可能暂时产生不同键，但它不会访问文件系统、
  不会跟随符号链接，也能处理扫描期间被删除的文件。后续扫描器会从统一的绝对根目录产生路径。
- 单条 upsert 先验证模型和 schema 边界；批量事务、扫描运行记录和失效记录清理属于 M1.2，
  不在本单元提前设计。

## 后果

- 新数据库和 schema 1 数据库都会安全迁移到 schema 2，已有 `nexus_metadata` 数据保持不变。
- 读取层可以按路径稳定定位记录，未来可以在 `path_display`、扩展名和修改时间上增加筛选。
- 扫描器仍需负责目录遍历、符号链接跳过、时间转换、失败统计和取消行为。
